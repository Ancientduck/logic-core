[DONE 2026-09-20] === AI COUNCIL PLAN (multi-agent system) — implemented as AI Council v2 (LOGIC + VINCI + SAGE, dispatch system live) ===

CONCEPT: 3 AI instances (different models) working together. Roles, not extra seats — supervisor is one of the 3.

ROLES / CASTING:
- Supervisor/Judge: strongest reasoning model (Claude Sonnet / GPT-5 / Gemini Pro class). Decomposes task, delegates, merges, decides. No economy here.
- Worker: strong domain model, mid-tier ok (DeepSeek V3/R1 for code, Qwen Coder for open weights). Critic catches its mistakes.
- Critic: detail-oriented, slightly weaker/different family (GPT-class / Gemini Flash). Never same model family as worker — same lineage = same blind spots.
- RULE: never two agents on the same model. Same-model ensembles = one opinion paid 3x.

PATTERN: Supervisor (2026 production default) + Critique loop (~1.2-1.5x cost).
- Supervisor delegates NON-OVERLAPPING subtasks; workers don't see each other's output during execution.
- No voting. One judge decides. Models argue, they don't vote.
- Hard cap: 2 critique rounds max, then supervisor merges best effort + reports unresolved. (Prevents infinite worker/critic disagreement loops.)

MERGING CODE:
1. Decompose along clean seams (one agent = one file/module for v1).
2. Define interfaces FIRST: a "contract" file with function signatures + data formats everyone codes against.
3. Workers emit artifacts (files or parseable JSON), never prose.
4. Supervisor integrates + resolves conflicts (name clashes, signature mismatches); sends targeted fixes back if needed.
5. Critic tests the ASSEMBLED whole, not individual pieces — integration bugs live between modules.

COMPLETION / SYNCHRONIZATION:
- v1: synchronous API calls (supervisor blocks until worker returns).
- Structured markers in prompts: "DONE + file path" or "BLOCKED + reason". Trust the marker, not the tone.
- Loop: Supervisor -> Worker (waits) -> artifact -> Critic (waits) -> PASS => deliver / ISSUES => back to Worker (max 2 rounds).

STATE / COMMUNICATION:
- Shared blackboard (JSON/dict or SQLite), orchestrator controls write access.
- Each agent gets ONLY the context for its subtask — never full shared chat history (3x token cost + echo chamber).
- Global state (task status) owned by supervisor.

ROUTING:
- All calls through OmniRoute (localhost:20128) — swapping a seat = one config line.
- Cheap classifier/router first: does this task even need multiple agents? Reserve council for high-stakes work.

COST NOTES:
- Debate/Council pattern = ~2.5x single-model cost (Microsoft Copilot Council). Critique variant only ~1.2x.
- Lean option: supervisor + critic (2 agents) captures most of the value.
- Third agent only worth it if tasks genuinely decompose into parallel work.

USE CASE: security testing council (own/authorized targets ONLY):
- Worker 1: recon/enumeration. Worker 2: attack surface analysis. Judge: filter false positives, rate exploitability.
- Scanners (Nuclei/ZAP) for breadth, council for depth (chaining findings, logic flaws).

=== PHONE <-> PC CONNECTION (own app pipeline) — 2026-09-20 ===
Decision made:
- No cloud brain for v1. PC off = system offline. Accepted.
- No port forwarding (BD ISPs use CGNAT; WAN IP likely 100.64.x.x, dead on arrival).
- Telegram bot rejected: same PC-on constraint, less control. Messenger (free on local carriers) already covers zero-MB emergency channel via chat_monitor + send_message_to_messenger.py.

Architecture:
1. FastAPI server on PC (logic_tools/) — the "brain". LOGIC runs it; exposes endpoints for commands, file access, status, alerts.
2. Tailscale (free, WireGuard-based) for transport — install on PC + phone, one shared account. CGNAT-proof, no ports opened, end-to-end encrypted, direct LAN connection when both devices home. Phone reachable from mobile data OR any Wi-Fi; needs SOME internet, not specifically MB.
3. Client: start as PWA (install from browser, one tap), native app later if needed. PWA talks to FastAPI over Tailscale IP (100.x.x.x:port).

Channels summary:
- Messenger = free emergency channel (works with 0 MB on BD carriers, fragile, PC must be on).
- Tailscale + FastAPI + PWA = proper interface (needs any signal, PC must be on).

Build order: FastAPI server -> Tailscale setup (user makes account, logs in both devices) -> PWA client -> features (alerts, file access, phone ADB relay).
